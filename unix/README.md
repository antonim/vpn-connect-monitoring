# VPN Connect Monitoring — Linux и macOS

Следит за тем, что VPN поднят в рабочее время, предупреждает уведомлением
со звуком при обрыве и ведёт журнал, по которому строится отчёт с графиком.

Обе системы используют один и тот же код на Python. Различаются только
адаптеры: определение VPN, уведомления, звук, автозапуск и значок.

## Установка на Ubuntu / Debian

**[Скачать .deb](https://github.com/antonim/vpn-connect-monitoring/releases/latest)**, затем:

```bash
sudo apt install ./vpn-connect-monitoring_*_all.deb
```

Именно `apt`, а не `dpkg -i`: он сам подтянет зависимости.

Дальше запустить из меню приложений или командой `vpn-connect-monitoring`.
Откроется окно настроек — выбрать своё подключение, при необходимости
поправить часы и дни, поставить галочку «Запускать при входе в систему».

## Установка на macOS

**[Скачать образ](https://github.com/antonim/vpn-connect-monitoring/releases/latest)**,
открыть двойным щелчком и перетащить «VPN Connect Monitoring» на ярлык
«Программы» в том же окне. Рядом лежит папка «Для терминала» — она нужна
только тем, кому нужна команда в терминале:

```bash
cd "/Volumes/VPN Connect Monitoring "*/"Для терминала"
./install.sh
```

Установка идёт в `~/.local`, права администратора не нужны.

Выкладывается и `.tar.gz` с тем же содержимым — для тех, кому образ
неудобен.

### Что требуется

Только `python3`. Ни PyObjC, ни виртуальных окружений, ни сторонних
библиотек: значок в строке меню и уведомления обращаются к AppKit
напрямую через `ctypes` из стандартной библиотеки — см. `objc_bridge.py`.

PyObjC для этого не годится принципиально: с macOS он не поставляется —
Apple убрала его вместе с системным Python 2.7 в macOS 12.3, — в Command
Line Tools его нет, а в питон из Homebrew `pip` не пускает, потому что тот
помечен externally-managed.

Отдельная ловушка: на macOS без установленных Command Line Tools
`/usr/bin/python3` — это заглушка, которая при первом вызове открывает
окно установки на полтора гигабайта. Launcher обращается к ней только
после проверки `xcode-select -p`, а если питона в системе нет вовсе —
показывает окно с тем, что нужно поставить.

### Первый запуск

Приложение не подписано в Apple, поэтому Gatekeeper блокирует его один
раз. На macOS 15 и новее обход правым щелчком убран: «Системные
настройки» → «Конфиденциальность и безопасность» → «Всё равно открыть».
На macOS 14 и старше — правый щелчок по значку → «Открыть».

При первом запуске откроется файл настроек со списком найденных
подключений в шапке — вписать нужное в `VpnTarget`. Значок появится
в строке меню; автозапуск включается там же, пунктом «Запускать при
входе в систему».

Из терминала:

```bash
~/.local/bin/vpn-connect-monitoring --list        # посмотреть подключения
~/.local/bin/vpn-connect-monitoring --daemon      # фоновый режим без значка
```

### Уведомления

Разрешение приходится выдать вручную, программно macOS такого не
позволяет: «Системные настройки» → «Уведомления» → «VPN Connect
Monitoring» → «Допуск уведомлений», стиль «Предупреждения».

Стиль имеет значение. «Баннеры» исчезают с экрана сами через несколько
секунд, и обрыв связи легко пропустить — ровно эта беда была в
Windows-версии. Программа просит «Предупреждения» по умолчанию ключом
`NSUserNotificationAlertStyle`, но он действует только при первой
регистрации приложения: выбор человека для macOS главнее.

Если уведомления приходят от имени «Python» — значит в системе
зарегистрировано несколько копий приложения, обычно после обновления,
когда старая версия осталась в Корзине. Раздел «Регистрация приложения»
в `tools/macos-check.sh` перечисляет все копии.

## Выбор подключения

Список приложение собирает само, вручную ничего искать не нужно:

```bash
vpn-connect-monitoring --list
```

**Linux.** Интерфейсы `wg*`, `tun*`, `tap*`, `ppp*` и подключения
NetworkManager типа `vpn`/`wireguard`. Подключения NetworkManager попадают
в список даже когда выключены — иначе выбрать нужное было бы нельзя.

**macOS.** Службы сетевых подключений из «Системных настроек»
(`scutil --nc`) — это встроенные IKEv2, IPsec и L2TP. Плюс интерфейсы
`utun` с назначенным адресом — их поднимают WireGuard, OpenVPN
и Tunnelblick.

Пустые `utun` из списка отбрасываются намеренно: macOS держит несколько
таких интерфейсов под свои службы вроде Private Relay и Handoff, и без
фильтра список состоял бы в основном из них.

В конфиге цель записывается с префиксом:

| Префикс | Пример | Где применяется |
|---|---|---|
| `iface:` | `iface:wg0`, `iface:utun4` | обе системы |
| `nm:` | `nm:office-vpn` | Linux, NetworkManager |
| `nc:` | `nc:Office VPN` | macOS, службы подключений |

## Автозапуск

**Linux** — файл в `~/.config/autostart`, галочка есть в окне настроек.

**macOS** — LaunchAgent в `~/Library/LaunchAgents`. Включить:

```bash
python3 -c "import sys; sys.path.insert(0,'$HOME/.local/lib'); from vpnmon import autostart; autostart.enable()"
```

Агент создаётся с `RunAtLoad`, но без `KeepAlive`: перезапускать
приложение, которое вы сами закрыли через меню, было бы навязчиво.

## Режим без графики

Для машины без рабочего стола или для systemd:

```bash
vpn-connect-monitoring --daemon
```

Ни GTK на Linux, ни AppKit на macOS в этом режиме не импортируются вовсе.
Уведомления всё равно отправляются, если в сессии есть чем; журнал ведётся
в любом случае.

Пример user-юнита `~/.config/systemd/user/vpn-connect-monitoring.service`:

```ini
[Unit]
Description=VPN Connect Monitoring
After=network.target

[Service]
ExecStart=/usr/bin/vpn-connect-monitoring --daemon
Restart=on-failure

[Install]
WantedBy=default.target
```

```bash
systemctl --user enable --now vpn-connect-monitoring
```

## Журнал и отчёт

Пункт **«Журнал подключения…»** в меню значка строит HTML-отчёт и открывает
его в браузере. То же самое из терминала:

```bash
vpn-connect-monitoring --report --open
```

В отчёте лента состояний за 24 часа, 3, 7 и 30 дней с переключением на
месте, доступность в процентах, суммарное и максимальное время без связи и
таблица обрывов. Файл самостоятельный — его можно переслать администратору.

Отчёт сделан в HTML, а не нарисован в окне, намеренно: так он работает и на
машине без графики, и его удобно отправлять как есть.

## Файлы

| Путь | Что это |
|---|---|
| `~/.config/vpn-connect-monitoring/config.ini` | Настройки, обычный текст |
| `~/.config/vpn-connect-monitoring/history.csv` | Журнал, `дата-время;состояние` |
| `~/.config/vpn-connect-monitoring/report.html` | Последний построенный отчёт |

Каталог `~/.config` используется и на macOS — вопреки тамошнему обычаю
хранить всё в `~/Library/Application Support`. Так конфиг и журнал
переносятся между системами без правок, а формат совпадает ещё
и с Windows-версией.

## Сборка

```bash
./build-deb.sh      # пакет для Ubuntu/Debian
./build-macos.sh    # архив для macOS
```

`build-deb.sh` требует только `dpkg-deb` из базовой Ubuntu. Пакет
архитектурно-независимый: внутри Python и текстовые файлы.

GTK и индикатор вынесены в `Recommends`, а не `Depends`: на сервере нужен
только `--daemon`, тянуть туда библиотеки рабочего стола незачем. Apt
в Ubuntu ставит `Recommends` по умолчанию, поэтому на настольной машине
всё приедет само.

`build-macos.sh` делает образ диска `.dmg` и архив `.tar.gz`. В отличие
от `build-deb.sh`, он работает **только на macOS**: пакету `.app` нужны
`osacompile`, `codesign`, `sips`, `iconutil` и `hdiutil`, а они входят
в macOS и больше нигде не встречаются. Собрать macOS-сборку в линуксовом
CI нельзя.

### Почему сборка привязана к Mac и что с этим можно сделать

Раньше архив собирался где угодно. Привязку создали три инструмента,
и обойти их не выходит:

| Инструмент | Зачем | Обходится |
|---|---|---|
| `codesign` | подписать пакет после сборки | нет — неподписанный пакет на Apple silicon не запускается (`Launch failed`), а любая правка внутри ломает подпись |
| `osacompile` | даёт Mach-O `applet` для `Contents/MacOS` | нет — это двоичный файл Apple |
| `hdiutil` | образ `.dmg` | нет без сторонних инструментов |
| `sips`, `iconutil` | значок `.icns` | да — формат простой, писать можно на Python |
| `plutil` | правка `Info.plist` | да — это обычный XML |

Два последних убрать реально, но смысла нет: первые три остаются.

Варианты, если возможность собирать где угодно понадобится снова:

1. **Оставить как есть**, релизы собирать на macOS-раннере. У GitHub
   Actions это `macos-latest`, для публичных репозиториев бесплатно.
   Сборка `.deb` не затрагивается, она по-прежнему идёт где угодно.

2. **Отказаться от `.app`** и вернуться к `.tar.gz` с `install.sh`.
   Программа продолжит работать целиком, но: установка снова вручную;
   уведомления пойдут от имени «Python» — подмена идентификатора требует
   зарегистрированного приложения, а регистрировать станет нечего, и
   разрешение придётся выдавать любой Python-программе на машине; стиль
   «Предупреждения» по умолчанию не выставить, останутся исчезающие
   баннеры; автозапуск снова будет ссылаться на интерпретатор и ломаться
   при его обновлении.

3. **Гибрид**: `.tar.gz` собирать везде, `.app` и `.dmg` — только когда
   инструменты нашлись. Изнанка в том, что под одним именем окажется
   разное содержимое в зависимости от машины сборки, и получатель не
   поймёт, почему у него уведомления от «Python», а у соседа нет.
   Тогда архивы придётся называть по-разному.

Решение за основным разработчиком. Пока действует первый вариант.

## Устройство адаптеров

| | Linux | macOS |
|---|---|---|
| Состояние VPN | `/sys/class/net` + `nmcli` | `scutil --nc` + `ifconfig` |
| Уведомления | `notify-send` | AppKit через `ctypes` |
| Звук | `pw-play` / `paplay` / `aplay` | `afplay` |
| Значок | AppIndicator (GTK) | `NSStatusItem` через `ctypes` |
| Автозапуск | `~/.config/autostart` | LaunchAgent |

Четыре решения, которые стоит понимать при доработке:

**Состояние интерфейса на Linux определяется по флагам, а не по
`operstate`.** У `tun`- и `wireguard`-интерфейсов `operstate` сплошь и
рядом равен `unknown` даже когда связь есть, и сравнение с `up` давало бы
постоянную ложную тревогу.

**На macOS `utun` без адреса не считается VPN.** Система держит такие
интерфейсы под свои нужды постоянно, и их наличие ничего не говорит
о подключении.

**Уведомления об обрыве на Linux отправляются с `--urgency critical`.**
В GNOME такой баннер висит, пока его не закроют. Исчезающий баннер — ровно
та причина, по которой обрывы пропускались в Windows-версии.

**На macOS уведомления показывает сама программа, а не `osascript`.**
У `osascript` изъян хуже, чем чужое имя отправителя: если уведомления
приложению «Script Editor», от имени которого он их шлёт, не разрешены,
сообщение не появляется вовсе — а вызов при этом завершается успешно.
Молчаливый отказ хуже явного, поэтому `osascript` оставлен запасным путём.

**Процесс подменяет себе `-[NSBundle bundleIdentifier]`.** Иначе центр
уведомлений показывает сообщения от имени «Python» с его ракетой: имя
и значок он берёт у главного бандла процесса, а Python во фреймворковой
сборке всегда объявляет главным свой `Python.app`. Это не обходится ни
расположением файлов внутри пакета, ни символическими ссылками, ни копией
бинарника — проверено, все три дают `org.python.python`.

**Исполняемым файлом `.app` обязан быть Mach-O.** Приложение, у которого
на этом месте лежит скрипт, macOS 15 не открывает вовсе: сначала
предлагает поставить Rosetta, не сумев определить архитектуру, затем
возвращает `-10669`. Поэтому пакет строится вокруг стандартного applet'а
из `osacompile`, а скрипт запуска переехал в `Contents/Resources`.

## Чего на macOS пока нет

**Окна настроек.** Пункт «Настройки…» открывает `config.ini` в текстовом
редакторе. Формат простой и описан выше, а после правки настройки
подхватываются пунктом «Проверить сейчас». Полноценное окно — заметный
объём кода ради полутора десятков полей.

**Мгновенной реакции на смену состояния сети.** Опрос идёт по таймеру,
поэтому обрыв замечается в пределах `IntervalSeconds` (10–3600 секунд).
Подписка на события `SCDynamicStore` дала бы мгновенную реакцию, но
потребовала бы отсрочки перед тревогой — иначе программа станет орать
при каждом ручном переключении VPN.
